# Форк OpenCode

Этот репозиторий — форк [OpenCode](https://github.com/anomalyco/opencode). Ниже описаны изменения, которые присутствуют именно в текущей ветке форка, а не гарантии upstream OpenCode.

Основное дополнение — опциональная защитная граница для действий агента: изоляция команд и локальных MCP-процессов через Linux `bubblewrap`, единая политика доступа к файловой системе для встроенных файловых инструментов, раздельные сетевые политики для инструментов, провайдеров моделей и MCP, фильтрация окружения и доверенные исходящие уведомления в Telegram с настраиваемым HTTP(S)-прокси. Кроме того, форк добавляет встроенную команду `/goal` для автономного выполнения сформулированной задачи.

> Важно: наличие этих механизмов в форке не означает, что upstream OpenCode предоставляет те же гарантии изоляции.

## Основные отличия от upstream

| Область                | Реализованное поведение                                                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Команды агента         | На Linux команды инструмента оболочки запускаются через `bwrap`, если включён `sandbox`. Изолируется всё дерево дочерних процессов.                                                                                 |
| Файловая система       | Рабочий каталог доступен на запись по умолчанию; дополнительные корни можно открыть только для чтения или для записи; `deny` маскирует запрещённые пути. Остальная файловая система хоста не монтируется в sandbox. |
| Встроенные инструменты | `read`, просмотр каталогов, `glob`, `grep`, `write`, `edit` и `apply_patch` проверяют ту же центральную файловую политику до доступа.                                                                               |
| Сеть                   | Отдельно задаются сеть команд (`tools`), возможность использовать провайдеры моделей (`provider`) и список разрешённых MCP по имени (`mcp.allow`).                                                                  |
| Локальные MCP          | При включённом основном sandbox каждый разрешённый локальный MCP запускается в отдельном `bwrap`; сеть по умолчанию отключена.                                                                                      |
| Окружение              | Режим `safe` передаёт командам только небольшой список безопасных переменных. Секреты Telegram и переменные прокси удаляются из недоверенного окружения даже при выключенном sandbox.                               |
| Уведомления            | Доверенный процесс OpenCode может отправлять односторонние уведомления Telegram о запросе внимания, завершении, ошибке и повторной попытке.                                                                         |
| Прокси                 | Для каждого адресата Telegram независимо выбирается прямое соединение, прокси из окружения или явный HTTP(S)-прокси.                                                                                                |
| Отказ по умолчанию     | Если запрошенную OS-изоляцию нельзя обеспечить, команда не запускается. Неизвестное имя в `mcp.allow` делает инициализацию MCP ошибочной.                                                                           |
| Автономная команда     | `/goal <задача>` разворачивается во встроенную инструкцию выполнить задачу до конца, вести список работ и запустить проверки.                                                                                       |

## Модель безопасности

В форке действуют три разных механизма, которые не следует смешивать.

1. **Система разрешений OpenCode** управляет запросами пользователю (`Allow once`, постоянное разрешение, отклонение) и правилами для инструментов. Это дополнительный слой пользовательской политики и интерфейса.
2. **Политика sandbox** вычисляет, разрешён ли конкретный путь, сеть инструментов, транспорт провайдера и MCP с данным именем. Эта политика применяется независимо от пользовательского ответа на запрос разрешения.
3. **OS-изоляция `bubblewrap`** ограничивает процессы оболочки и локальных MCP на уровне пространств имён и таблицы монтирования Linux. Встроенные файловые инструменты работают внутри доверенного процесса OpenCode, поэтому для них применяется программная проверка центральной файловой политики, а не отдельный `bwrap`.

Концептуальное правило доступа:

```text
эффективный_доступ = разрешено_sandbox И разрешено_системой_разрешений
```

Положительный ответ `Allow once` и правило `external_directory=allow` не расширяют корни, заданные sandbox. Сначала выполняется проверка sandbox; только после неё может применяться обычная система разрешений. Внутренний служебный флаг обхода проверки рабочего каталога также не обходит sandbox.

Для команд оболочки при включённом sandbox отдельные запросы `external_directory` не используются: реальной границей служат монтирования `bwrap`. Другие разрешения, в том числе разрешение на сам вызов оболочки, продолжают действовать. Для встроенных файловых инструментов обе проверки сохраняются.

Проверка путей канонизирует существующие пути через `realpath`. Для ещё не созданного файла канонизируется ближайший существующий родитель, после чего добавляется отсутствующий суффикс. Это блокирует обычный выход через символьную ссылку на файл, каталог или существующий родитель нового файла. Однако проверка и последующее использование пути являются разными операциями: остаётся классическая гонка TOCTOU, если доверенный параллельный процесс успеет заменить компонент пути после проверки. Реализация не заявляет защиты от такой гонки.

## Требования

- OS-изоляция реализована **только для Linux**.
- В `PATH` должен находиться исполняемый файл `bwrap` из пакета Bubblewrap.
- Для внутреннего loopback-реле restricted-режима требуется `/usr/bin/python3` (или рабочий `python3` в `PATH`); без него restricted-команда закрывается с ошибкой.
- Ядро и политика безопасности хоста должны разрешать необходимые непривилегированные пространства имён пользователя.
- Запуск от `root` и Docker/Podman daemon не требуются.
- `bwrap` не встраивается в сборку OpenCode и должен быть установлен на хосте отдельно. Для прокси уведомлений зависимость HTTP-клиента входит в пакет OpenCode.

Установка в Ubuntu:

```bash
sudo apt update
sudo apt install bubblewrap
```

Если `sandbox` запрошен, но платформа не Linux, `bwrap` отсутствует, рабочий каталог или обязательный разрешённый путь не существует, путь в `read`/`write` не абсолютный либо создание пространств имён завершается ошибкой, команда не выполняется. Автоматического небезопасного повторного запуска без sandbox нет.

На неподдерживаемой платформе OpenCode можно использовать только с выключенным `sandbox`; в таком режиме OS-изоляции команд и локальных MCP нет. Программная файловая политика также активна только при включённом sandbox.

## Ubuntu 24.04 и AppArmor

На Ubuntu 24.04 запуск непривилегированного Bubblewrap может завершиться сообщением:

```text
bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted
```

Одна из возможных причин — ограничение AppArmor на непривилегированные пользовательские пространства имён. Для **временной диагностики** на тестовой машине ограничение можно отключить до следующего изменения параметра или перезагрузки:

```bash
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0
```

Вернуть ограничение:

```bash
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=1
```

Предупреждения:

- не запускайте OpenCode от `root` только ради работы sandbox;
- глобальное отключение этого ограничения AppArmor не рекомендуется как постоянная производственная настройка;
- для постоянной эксплуатации предпочтительнее целевая политика AppArmor, разрешающая необходимое конкретному исполняемому файлу;
- репозиторий не устанавливает и не активирует профиль AppArmor автоматически: это системная настройка администратора хоста.

### Целевой профиль AppArmor для `bwrap`

Вместо глобального изменения `kernel.apparmor_restrict_unprivileged_userns` можно разрешить создание пользовательских пространств имён только исполняемому файлу Bubblewrap. Ниже приведён минимальный профиль для штатного пакета Ubuntu 24.04. Он оставляет сам `bwrap` неконфинированным правилами AppArmor, но добавляет ему право `userns`; фактическую изоляцию дочернего процесса по-прежнему строит сам Bubblewrap.

Сначала проверьте реальный путь и установленные компоненты:

```bash
command -v bwrap
readlink -f "$(command -v bwrap)"
command -v apparmor_parser
```

Для пакета Ubuntu ожидаются `/usr/bin/bwrap` и установленный `apparmor_parser`. Если последней команды нет, установите пакет AppArmor:

```bash
sudo apt update
sudo apt install apparmor
```

Если канонический путь равен `/usr/bin/bwrap`, создайте локальный профиль:

```bash
sudo tee /etc/apparmor.d/opencode-bwrap >/dev/null <<'EOF'
abi <abi/4.0>,
include <tunables/global>

profile opencode-bwrap /usr/bin/bwrap flags=(unconfined) {
  userns,
}
EOF
```

Не копируйте в правило путь к скрипту запуска OpenCode: пользовательское пространство имён создаёт процесс `bwrap`, поэтому профиль прикрепляется к его реальному исполняемому файлу. Если `readlink` показывает не `/usr/bin/bwrap`, замените `/usr/bin/bwrap` после имени профиля на выведенный абсолютный путь. Не подставляйте в системный файл непроверенный вывод команды. После обновления или переноса Bubblewrap путь следует проверить снова.

До загрузки попросите парсер только проверить синтаксис, затем активируйте профиль:

```bash
sudo apparmor_parser -Q /etc/apparmor.d/opencode-bwrap
sudo apparmor_parser -r /etc/apparmor.d/opencode-bwrap
```

Файл в `/etc/apparmor.d` сохраняется после перезагрузки и загружается службой AppArmor. Возвратите глобальное ограничение, если ранее отключали его для диагностики:

```bash
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=1
```

Такой профиль уже, чем глобальное разрешение непривилегированных пользовательских пространств имён, но не является разрешением только для OpenCode: любой пользователь, которому разрешено запускать профилированный `bwrap`, сможет запросить `userns` через Bubblewrap. Не добавляйте `userns` в широкий профиль оболочки, Bun или всех пользовательских программ и не делайте `bwrap` setuid ради обхода ошибки.

### Проверка и удаление профиля

Убедитесь, что профиль загружен:

```bash
sudo apparmor_status | grep opencode-bwrap
```

Затем выполните короткую проверку Bubblewrap от имени обычного пользователя, **без `sudo`**:

```bash
bwrap --die-with-parent --new-session --unshare-all \
  --ro-bind / / \
  --dev /dev \
  --tmpfs /tmp \
  --chdir /tmp \
  -- /bin/true
```

После этого повторите команду OpenCode с включённым sandbox. Если ошибка сохраняется, изучите сообщения ядра/AppArmor, а не расширяйте профиль вслепую:

```bash
sudo journalctl -k --since "10 minutes ago" | grep -E 'apparmor|DENIED|bwrap'
```

Ограничения контейнера, seccomp или политика хостинга могут блокировать пространства имён независимо от AppArmor; целевой профиль не обходит такие ограничения. Не переключайте профиль в режим жалоб для постоянной эксплуатации.

Чтобы полностью отменить настройку, сначала выгрузите профиль, затем удалите файл:

```bash
sudo apparmor_parser -R /etc/apparmor.d/opencode-bwrap
sudo rm /etc/apparmor.d/opencode-bwrap
```

## Конфигурация sandbox

Практическая строгая основа:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "read": [],
      "write": [],
      "deny": []
    },
    "network": {
      "tools": "none",
      "provider": "configured",
      "mcp": {
        "allow": []
      }
    },
    "environment": "safe"
  }
}
```

### Включение и значения по умолчанию

Поле `sandbox` принимает логическое значение или объект.

| Значение               | Результат                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| поле отсутствует       | sandbox выключен                                                                                                                                       |
| `false`                | sandbox выключен                                                                                                                                       |
| `true`                 | sandbox включён с файловыми корнями по умолчанию, сетью инструментов `none`, провайдерами `configured`, прежним режимом выбора MCP и окружением `safe` |
| `{}`                   | sandbox включён; `enabled` считается истинным, пока явно не задано `false`                                                                             |
| `{ "enabled": false }` | OS-изоляция, файловая политика и безопасное окружение выключены; явно заданная объектная политика `network.provider`/`network.mcp` всё ещё учитывается |

`enabled` управляет именно процессной и файловой изоляцией. Текущая реализация читает объектные настройки доверенной сети провайдера и MCP независимо от `enabled`. Поэтому сочетание `enabled: false` с `network.provider: "disabled"` всё равно отключает провайдер, а `network.mcp.allow` всё равно ограничивает MCP. Чтобы полностью вернуться к прежнему поведению без sandbox-политик, удалите поле `sandbox` или задайте всё поле как `false`, а не объект с `enabled: false`.

Полная текущая форма объекта:

```json
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "read": ["/абсолютный/путь/только-для-чтения"],
      "write": ["/абсолютный/путь/для-записи"],
      "deny": ["/абсолютный/запрещённый/путь"]
    },
    "network": {
      "tools": "none",
      "provider": "configured",
      "mcp": {
        "allow": ["имя-mcp-из-раздела-mcp"]
      }
    },
    "environment": "safe"
  }
}
```

Допустимые значения:

- `enabled`: `true` или `false`;
- `filesystem.read`, `filesystem.write`, `filesystem.deny`: массивы строк с абсолютными путями;
- `network.tools`: `"none"`, `"full"` или объект `{ "mode": "restricted", "allow": [...] }`;
- `network.provider`: `"configured"` или `"disabled"`;
- `network.mcp.allow`: обязательный массив имён, если объект `mcp` присутствует;
- `environment`: `"safe"` или `"all"`.

### Политика файловой системы

- Активный рабочий каталог всегда добавляется в корни записи и, следовательно, чтения.
- `filesystem.read` добавляет существующие корни только для чтения.
- `filesystem.write` добавляет существующие корни для чтения и записи.
- `filesystem.deny` запрещает путь и всё под ним, даже если они находятся внутри рабочего или другого разрешённого корня. Запрещённый существующий каталог перекрывается пустой `tmpfs`, существующий файл — `/dev/null` только для чтения.
- Пути `read` и `write` должны быть абсолютными и существовать при построении политики. Путь `deny` тоже должен быть абсолютным, но может ещё не существовать.
- Дубликаты после канонизации удаляются.
- Относительные компоненты и символьные ссылки не позволяют выйти из разрешённого канонического корня при обычной проверке.
- Рекурсивное чтение корня отклоняется целиком, если внутри него расположен любой `deny`. Поэтому `glob`, `grep` или чтение каталога над запрещённым подкаталогом нужно начинать с более узкого разрешённого пути, который не содержит `deny`.

В sandbox дополнительно монтируются:

- `/bin`, `/usr`, `/lib`, `/lib64`, если они существуют, только для чтения;
- минимальные файлы учётных записей, DNS и TLS: существующие `/etc/ca-certificates`, `/etc/group`, `/etc/hosts`, `/etc/nsswitch.conf`, `/etc/passwd`, `/etc/pki`, `/etc/resolv.conf`, `/etc/ssl`;
- отдельный `/dev` и пустой временный `/tmp`.

`/proc`, `/sys` и `/var/run` не монтируются. `/run` отсутствует в режимах `none`/`full`; в `restricted` создаётся только `/run/opencode-network` с приватным сокетом брокера и релеем. Сокеты Docker, Podman, containerd, D-Bus и SSH-агента не становятся доступны автоматически.

Пример с дополнительными корнями:

```json
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "read": ["/workspace/shared"],
      "write": ["/workspace/generated"],
      "deny": ["/workspace/project/.env", "/workspace/project/private"]
    }
  }
}
```

### Встроенные файловые инструменты

Единая политика применяется до файловой операции:

- `read` проверяет файл как чтение; при чтении каталога дополнительно требует безопасного рекурсивного дерева;
- `glob` и `grep` требуют разрешения на рекурсивное чтение выбранного пути;
- `write` и `edit` требуют разрешения на запись целевого пути;
- `apply_patch` сначала проверяет **все** исходные и целевые пути всех фрагментов, включая путь назначения при перемещении, и лишь затем читает или изменяет файлы. Запрещённый фрагмент не должен оставлять частично применённый патч.

Это программное ограничение внутри процесса, а не отдельное пространство имён. Оно закрывает штатные пути доступа перечисленных инструментов, но не превращает плагины или другие внутренние подсистемы в недоверенный код.

### Сетевая политика

Объектная форма разделяет три границы:

```json
{
  "sandbox": {
    "enabled": true,
    "network": {
      "tools": "none",
      "provider": "configured",
      "mcp": {
        "allow": ["local-filesystem", "company-api"]
      }
    }
  }
}
```

#### `network.tools`

- `"none"` — `bwrap` оставляет команду и всё её дерево в отдельном сетевом пространстве имён без общей сети хоста;
- `{ "mode": "restricted", "allow": [...] }` — изолированное пространство имён сохраняется, а HTTP/HTTPS разрешены только через доверенный брокер для явно перечисленных имён и портов;
- `"full"` — в `bwrap` передаётся `--share-net`, то есть процесс сознательно получает сеть хоста без фильтрации адресов.

По умолчанию используется `"none"`. Ограниченный режим настраивается так:

```json
{
  "sandbox": {
    "enabled": true,
    "network": {
      "tools": {
        "mode": "restricted",
        "allow": [
          { "host": "github.com", "ports": [443] },
          { "host": "codeload.github.com", "ports": [443] },
          { "host": "raw.githubusercontent.com", "ports": [443] },
          { "host": "objects.githubusercontent.com", "ports": [443] },
          { "host": "git.corp.example", "ports": [443], "private": true }
        ]
      },
      "provider": "configured",
      "mcp": { "allow": [] }
    }
  }
}
```

Каждое правило обязательно содержит `host` и непустой массив `ports`; все порты должны находиться в диапазоне 1–65535. Порта по умолчанию и значения «все порты» нет. Имена приводятся к нижнему регистру, завершающая точка удаляется, IDN переводятся в ASCII/Punycode. IP-литерал является отдельным именем правила: разрешение `github.com` не разрешает прямое обращение к IP, в который он резолвится.

Необязательное `includeSubdomains: true` включает само имя и только дочерние DNS-метки. Например, правило для `githubusercontent.com` допускает `raw.githubusercontent.com`, но не `evilgithubusercontent.com`. Шаблоны и произвольные суффиксы не поддерживаются.

DNS выполняет доверенный брокер после проверки имени и порта. По умолчанию результат DNS отклоняется, если это loopback, RFC1918/private, link-local, unspecified, multicast, IPv4-mapped IPv6 или документальный/специальный диапазон. `private: true` разрешает частные адреса только для совпавшего явного правила, что подходит для HTTPS-сервера компании; имя и порт всё равно проверяются. Не задавайте `private: true` публичным доменам без необходимости.

Архитектура не использует `--share-net`: процесс остаётся без маршрута во внешнюю сеть, а loopback-релей передаёт HTTP-прокси-трафик через приватный Unix-сокет брокеру в доверенном процессе. Поэтому `curl --noproxy '*'`, отключение прокси в Git/Wget, `nc`, Python `socket` и прямой IP не получают обходного пути. Переменные `HTTP_PROXY`, `HTTPS_PROXY`, `http_proxy` и `https_proxy` добавляются OpenCode после обычной фильтрации окружения только для совместимости клиентов; они не являются границей безопасности и не содержат учётных данных хостового прокси.

Поддерживаются обычный HTTP и HTTPS через `CONNECT`. TLS не перехватывается, проверка сертификатов не отключается. Политика применяется к каждому новому соединению, поэтому переход HTTP на другой хост завершится отказом, пока второй хост не разрешён отдельно. Для Git поддерживается HTTPS (`git clone`, `fetch`, `submodule update`) при наличии всех используемых хостов в списке. GitHub в разных операциях может обращаться к `github.com`, `codeload.github.com`, `raw.githubusercontent.com` и `objects.githubusercontent.com`; автоматических разрешений нет. **Git по SSH в restricted-режиме не поддерживается: используйте HTTPS или `tools: "full"`.**

HTTPS является непрозрачным туннелем. Разрешение `github.com:443` разрешает любой HTTPS-ресурс на этом имени: без MITM TLS невозможно безопасно ограничить путь URL, организацию или отдельный репозиторий. Сервер с корпоративным CA требует обычной явной файловой политики для CA bundle; `GIT_SSL_NO_VERIFY` и аналоги не используются.

Если брокер, Unix-сокет, внутренний релей или пространство имён нельзя создать, команда завершается с ошибкой и не повторяется с полной сетью. Ограниченная политика относится только к shell/tools. Провайдер сохраняет отдельную семантику `configured`/`disabled`, а локальные MCP по-прежнему имеют только собственные `none`/`full` и не наследуют restricted-политику инструментов.

#### `network.provider`

- `"configured"` — доверенный родительский процесс может создавать настроенные клиенты моделей;
- `"disabled"` — разрешение/инициализация клиента модели завершается ошибкой `Provider networking is disabled by sandbox network policy`.

По умолчанию используется `"configured"`. Трафик модели идёт из доверенного процесса OpenCode и никогда не проходит через сетевое пространство команды оболочки.

#### `network.mcp.allow`

Массив содержит **имена записей** верхнеуровневого раздела `mcp`, а не хосты. В объектной форме сети отсутствие `mcp` или `allow` означает пустой список: ни один MCP не разрешён. Имя, которого нет в конфигурации `mcp`, приводит к ошибке инициализации. Запись с `enabled: false` остаётся выключенной, даже если её имя присутствует в списке.

Разрешённый удалённый MCP подключается из доверенного процесса только к URL, статически указанному в его одноимённой конфигурации. При явной объектной политике реализация также проверяет совпадение URL с настроенной разрешённой записью. Неразрешённый MCP получает состояние ошибки политики и не подключается.

#### Совместимая логическая форма сети

Сохранена прежняя форма:

```json
{
  "sandbox": {
    "network": false
  }
}
```

- `network: false` означает `tools: "none"`;
- `network: true` означает `tools: "full"`;
- в обеих логических формах провайдеры остаются `configured`, а выбор MCP сохраняет прежнее поведение: настроенные включённые MCP разрешены без списка имён.

Чтобы получить явную политику MCP или отключить провайдеры, используйте объектную форму.

### Локальные MCP-серверы

Пример:

```json
{
  "sandbox": {
    "enabled": true,
    "network": {
      "tools": "none",
      "provider": "configured",
      "mcp": {
        "allow": ["local-filesystem"]
      }
    }
  },
  "mcp": {
    "local-filesystem": {
      "type": "local",
      "command": ["local-filesystem-mcp"],
      "cwd": ".",
      "environment": {
        "MCP_MODE": "readonly"
      },
      "sandbox": {
        "network": "none"
      }
    }
  }
}
```

При включённом основном sandbox локальный MCP:

- получает собственный процесс `bwrap` с той же файловой политикой;
- использует рабочий каталог MCP (`cwd`, относительный к рабочему каталогу проекта) как активный рабочий корень, доступный на запись;
- по умолчанию имеет `sandbox.network: "none"` независимо от `network.tools`;
- может получить полную сеть хоста только через явное `mcp.<имя>.sandbox.network: "full"`;
- получает безопасное базовое окружение плюс значения, явно заданные в `mcp.<имя>.environment`.

Если основной sandbox выключен, `mcp.<имя>.sandbox.network` не создаёт изоляцию сам по себе: локальный MCP запускается обычным способом. При этом чувствительные переменные уведомлений и прокси всё равно удаляются из наследуемого окружения, после чего явно настроенный `mcp.<имя>.environment` может сознательно добавить их обратно.

### Фильтрация окружения

При включённом sandbox значение по умолчанию — `environment: "safe"`. Команде оболочки передаются только определённые и имеющие значение переменные:

```text
COLORTERM
LANG
LC_ALL
LC_CTYPE
PATH
TERM
TZ
```

Не наследуются ключи API провайдеров, облачные учётные данные, OAuth-токены, `SSH_AUTH_SOCK` и переменные прокси. Режим `environment: "all"` передаёт остальные переменные процесса и поэтому может раскрыть команде секреты; его следует включать только осознанно.

Независимо от `safe`/`all` и даже при выключенном sandbox из окружения команд и локальных MCP без учёта регистра удаляются:

```text
OPENCODE_TELEGRAM_BOT_TOKEN
OPENCODE_TELEGRAM_CHAT_ID
OPENCODE_TELEGRAM_PROXY
HTTP_PROXY
HTTPS_PROXY
ALL_PROXY
NO_PROXY
```

Для локального MCP значения из его собственного поля `environment` накладываются после фильтрации. Это намеренный доверенный канал конфигурации. Плагины, напротив, выполняются внутри процесса OpenCode и могут читать его окружение.

## Уведомления Telegram

`notification` — объект адресатов с произвольными именами. Сейчас реализован единственный тип провайдера: `telegram`.

```json
{
  "$schema": "https://opencode.ai/config.json",
  "notification": {
    "personal": {
      "type": "telegram",
      "enabled": true,
      "botToken": "{env:OPENCODE_TELEGRAM_BOT_TOKEN}",
      "chatId": "{env:OPENCODE_TELEGRAM_CHAT_ID}",
      "proxy": {
        "mode": "direct"
      },
      "events": {
        "attention": true,
        "completed": {
          "enabled": true,
          "after": "30s"
        },
        "failed": true,
        "retry": false
      }
    }
  }
}
```

Для включённого адресата обязательны непустые `botToken` и `chatId`. Подстановка `{env:ИМЯ}` выполняется до проверки схемы, поэтому секреты удобно держать в окружении:

```bash
export OPENCODE_TELEGRAM_BOT_TOKEN='123456:секрет'
export OPENCODE_TELEGRAM_CHAT_ID='123456789'
```

`enabled` можно не указывать: адресат включён, если значение не равно `false`. Выключенный адресат может не содержать `botToken` и `chatId`.

Уведомления только исходящие. Реализация вызывает Telegram Bot API `sendMessage` по HTTPS; она не опрашивает Telegram, не принимает webhook и не позволяет удалённо подтвердить разрешение или управлять OpenCode.

### События и значения по умолчанию

| Событие     | По умолчанию        | Когда отправляется                                                                                                                                                                         |
| ----------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `attention` | включено            | При запросе разрешения или вопросе пользователю. Для вопроса включаются текст и до пяти вариантов ответа.                                                                                  |
| `completed` | включено, порог `0` | После реального перехода сессии из `busy` в `idle`, если нет ожидающего ответа пользователя и длительность не меньше `after`.                                                              |
| `failed`    | включено            | При терминальной ошибке сессии, когда после ошибки сессия переходит в `idle`. Если после ошибки снова начинается `busy`, ошибка считается восстанавливаемой и уведомление не отправляется. |
| `retry`     | выключено           | При статусе повторной попытки; содержит номер попытки, время до следующей попытки и сообщение.                                                                                             |

Для `attention`, `failed` и `retry` допустимы `true`, `false` либо объект `{ "enabled": true|false }`. Для `completed` допустимы логическое значение либо объект с обязательным `enabled` и необязательным `after`.

`after` — строка из неотрицательного числа, включая десятичную дробь, и единицы `ms`, `s`, `m` или `h`: например, `500ms`, `30s`, `2m`, `1h`. Другие формы отклоняются при загрузке конфигурации.

Одинаковое событие с теми же `sessionID`, типом и идентификатором подавляется в течение 30 секунд. Отдельные запросы разрешения не склеиваются. Сообщение очищается от возврата каретки и нулевых байтов, ссылки вида `{env:...}` заменяются на `[redacted]`; фрагменты данных и итоговый текст ограничиваются по длине.

Доставка выполняется параллельно всем подходящим адресатам, выполняется по возможности и имеет тайм-аут 10 секунд на HTTP-запрос. Ошибка Telegram или прокси записывается как предупреждение без секретных транспортных деталей и не завершает задачу агента с ошибкой. Автоматической прямой повторной попытки после сбоя настроенного прокси нет.

### Прокси для доверенного HTTP

Прокси задаётся отдельно для каждого адресата и применяется только к этому доверенному назначению Telegram. Он не меняет транспорт моделей, MCP, плагинов, загрузок или инструментов.

#### Прямое соединение

Если `proxy` отсутствует или имеет вид ниже, используется прямой HTTPS:

```json
{
  "proxy": {
    "mode": "direct"
  }
}
```

#### Прокси из окружения

```json
{
  "proxy": {
    "mode": "environment"
  }
}
```

Для адреса `https://api.telegram.org` проверяются в таком порядке:

1. `https_proxy`, затем `HTTPS_PROXY`;
2. если они отсутствуют — `all_proxy`, затем `ALL_PROXY`;
3. `no_proxy` имеет приоритет над `NO_PROXY` и может отменить прокси.

`NO_PROXY`/`no_proxy` поддерживает `*`, точные имена, суффиксы с начальной точкой или `*` и необязательный порт. Если подходящий прокси в окружении отсутствует либо адрес исключён, соединение будет прямым. Системные настройки прокси рабочего стола Windows, macOS или Linux автоматически не обнаруживаются.

#### Явный URL прокси

```json
{
  "proxy": {
    "mode": "url",
    "url": "{env:OPENCODE_TELEGRAM_PROXY}"
  }
}
```

Например:

```bash
export OPENCODE_TELEGRAM_PROXY='http://127.0.0.1:7890'
```

Поддерживаются URL со схемой `http://` или `https://`, в том числе с учётными данными в URL. `socks5://` и `socks5h://` не поддерживаются и отклоняются схемой конфигурации. Для Telegram прокси использует HTTP `CONNECT`, а TLS остаётся сквозным между OpenCode и `api.telegram.org`. Обычный прокси видит имя и порт назначения, но не токен и текст внутри TLS. Прокси с доверенным на хосте перехватом TLS способен прочитать трафик и поэтому входит в доверенную границу.

### Защита секретов

- URL Telegram с токеном не записывается в журнал при ошибке доставки.
- Аутентифицированный URL прокси, заголовок авторизации и исходная транспортная ошибка не включаются в предупреждение уведомлений.
- Переменные Telegram и прокси удаляются из наследуемого окружения оболочки и локального MCP, если MCP не получил значение явно.
- Сеть Telegram принадлежит доверенному родительскому процессу и не требует `network.tools: "full"` и не добавляет Telegram в `mcp.allow`.
- Плагины являются доверенным кодом внутри процесса; sandbox не защищает токены от вредоносного плагина.

## Команда `/goal`

Форк регистрирует встроенную команду:

```text
/goal добавить проверку работоспособности сервиса
```

Аргументы подставляются во встроенный шаблон, который просит агента:

- воспринимать запрос как задачу на исполнение, а не только как просьбу дать совет или план;
- изучить проект и локальные инструкции;
- создать и поддерживать конкретный список работ с одним активным пунктом;
- реализовать сопутствующие тесты, документацию, генерацию и миграции, если они действительно нужны;
- запускать релевантные тесты, проверку типов, линтеры и сборку;
- продолжать независимую работу при частичной блокировке и не объявлять успех до доступной проверки результата.

Это инструкция модели, а не отдельный планировщик, демон или новая граница безопасности. Фактическое поведение по-прежнему зависит от модели, доступных инструментов, разрешений и sandbox.

## Границы и известные ограничения

- Изолируются команды инструмента оболочки и локальные MCP. LSP-серверы, форматтеры, PTY, установка плагинов и другие управляемые OpenCode подпроцессы не становятся их потомками автоматически и сохраняют прежнюю модель доверия.
- Удалённые MCP, клиенты моделей и Telegram работают в доверенном процессе. Для них `bwrap` не применяется.
- Плагины выполняются в процессе и полностью доверены.
- Нет фильтрации системных вызовов сверх границ, создаваемых пространствами имён Bubblewrap, нет лимитов CPU/памяти/числа процессов и нет квот диска.
- Restricted-фильтрация ограничена HTTP/HTTPS и парой «имя назначения + порт»; она не различает пути, репозитории или содержимое сквозного TLS-туннеля.
- `tools: "none"` не является политикой фильтрации трафика доверенного процесса; оно относится только к дереву sandbox-команды.
- Пустой `/tmp` доступен процессам внутри `bwrap`, но не добавляется в разрешённые корни встроенных файловых инструментов.
- Файловая проверка встроенных инструментов основана на путях и подвержена описанной выше гонке TOCTOU.
- `environment: "all"` осознанно ослабляет защиту секретов, кроме небольшого набора переменных Telegram/прокси, которые форк удаляет всегда.
- Включение `network: "full"` у локального MCP доверяет его процессу сеть хоста; оно не ограничивает назначения.
- Изоляция зависит не только от наличия `bwrap`, но и от настроек ядра, контейнера, seccomp и LSM/AppArmor хоста.

## Проверка установки

Проверить наличие Bubblewrap:

```bash
command -v bwrap
bwrap --version
```

Минимальная ручная проверка строгой конфигурации:

1. Включите `sandbox` с `network.tools: "none"` и `environment: "safe"`.
2. Попросите агента выполнить команду чтения файла за пределами рабочего каталога — операция должна завершиться отказом, а не запросом, расширяющим sandbox.
3. Попросите выполнить сетевое соединение из оболочки — оно должно завершиться ошибкой.
4. Убедитесь, что настроенный провайдер модели продолжает работать при `provider: "configured"`: его сеть отделена от сети инструментов.
5. Добавляйте абсолютные пути в `filesystem.read` или `filesystem.write` только после оценки содержащихся в них данных.

Ручная проверка restricted-режима должна выполняться собранным бинарным файлом с конфигурацией из примера выше:

```bash
git ls-remote https://github.com/ORG/REPOSITORY.git  # успешно для существующего публичного репозитория
curl https://github.com                              # успешно
curl https://example.com                             # отказ политики
curl --noproxy '*' https://example.com               # прямой маршрут отсутствует, тоже отказ
python3 -c 'import socket; socket.create_connection(("example.com", 443))' # отказ
# IP, полученный для github.com, также отклоняется без отдельного правила IP-литерала
```

При диагностике сначала проверьте наличие `bwrap`, допустимость user/network namespaces и корректность каждого `host`/`ports`. Код HTTP 403 с текстом `Sandbox network policy denied: host=... port=...` означает отсутствие совпавшего правила либо запрет частного результата DNS. Для внутреннего HTTPS-сервера добавьте `private: true` только его явному правилу. Ошибка 502 означает, что разрешённое назначение не удалось разрешить или подключить. При redirect добавьте целевой хост отдельным правилом. Не исправляйте такие ошибки включением `GIT_SSL_NO_VERIFY`, передачей секретов прокси или заменой restricted на `full`, не оценив последствия.

Для проверки реализации в исходном дереве релевантны тесты sandbox, файловых инструментов, конфигурации уведомлений, движка уведомлений и прокси. Запускайте их из каталога пакета, а не из корня репозитория:

```bash
cd packages/opencode
bun test test/sandbox/sandbox.test.ts test/tool/external-directory.test.ts
bun test test/notification/config.test.ts test/notification/notification.test.ts test/notification/proxy.test.ts
bun typecheck
```
